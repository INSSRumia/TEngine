## Context

当前远征已经具备最小闭环，但其静态结构仍以线性节点链为基础，运行时也主要依赖固定顺序推进。这样的模型无法稳定支持三类关键扩展：同一个 Event 被多个节点复用但出口逻辑不同；根据道具、历史选择、标记或计数器决定后续路线；在远征中后段动态插入新的事件或支线节点。

本次设计的目标不是直接做成“任意图编辑器”，而是在当前远征架构上建立一套清晰、可配置、可逐步扩展的分支模型。用户已经明确确认两个关键约束：Event 只定义内容和选项，不承载出口逻辑；出口逻辑属于 Node，并且按选项分支时必须以 `OptionId` 映射出口，而不是使用脆弱的 option index。

## Goals / Non-Goals

**Goals:**
- 将远征从固定线性 `route + currentIndex` 模式升级为“静态图 + 运行时待执行节点队列”模式。
- 引入节点级路由策略，支持固定出口、按选项出口、按条件出口。
- 引入远征黑板，统一承载标记、道具、历史选择、计数器等运行时状态。
- 允许同一个 Event 在不同 Node 中复用，同时由各自 Node 定义不同的出口逻辑。
- 为动态插入事件或支线节点提供明确的运行时入口。
- 在计划中继续保留人工协作边界：若 schema 或数据调整需要修改 `xlsx`，必须先通知用户手工修改。

**Non-Goals:**
- 不在这次变更中构建通用可视化图编辑器。
- 不在这次变更中设计完整的权重随机图生成系统。
- 不在这次变更中把所有分支逻辑都绑定到 Effect 系统里。
- 不在这次变更中修改 JSON/bytes 生成策略。

## Decisions

### 1. 运行时推进改为待执行节点队列，而不是索引递增
- 选择：在 `ExpeditionRunState` 中引入 `PendingNodeQueue` 或等价的待执行节点序列，作为“接下来实际要执行什么”的唯一来源。
- 原因：分支选择和动态插入节点都无法用单一 `CurrentNodeIndex` 优雅表达；队列能自然支持前插、尾插和跳转。
- 备选方案：
  - 继续沿用 `CurrentNodeIndex`：只能稳定处理线性推进。
  - 直接维护完整运行时图结构：过重，不适合当前阶段。

### 2. 静态配置仍然是图，但 Event 只做内容模板
- 选择：静态配置中保留节点、出口、条件等图结构；Event 仅定义内容和选项本身，不携带出口语义。
- 原因：同一个 Event 可在多个 Node 中复用，而不同 Node 的出口策略可能完全不同。
- 备选方案：
  - 在 Event 或 Option 上直接绑定出口：会破坏 Event 的可复用性。

### 3. 节点路由策略使用 enum，而不是 bool
- 选择：为 Node 增加 `RoutePolicy`，至少支持：
  - `FixedNext`
  - `BySelectedOption`
  - `ByConditions`
- 原因：bool 只能表达两态，而远征分支很快会超过两种路由模式；enum 可读性更高，也更容易扩展。
- 备选方案：
  - 使用 `bool` 标记是否按选项出口：后续会不断叠加额外 bool，配置会很快失控。

### 4. 按选项分支使用 `OptionId -> TransitionId` 映射，不使用 option index
- 选择：Node 级配置中显式声明 `OptionId` 到 `TransitionId` 的映射表。
- 原因：index 对选项顺序敏感，任何插入、重排或文案调整都可能让路由失效；`OptionId` 稳定且可读。
- 备选方案：
  - 根据选项 index 直接匹配出口：实现简单，但维护风险高。

### 5. 黑板用于长期状态，不用于所有即时跳转
- 选择：远征黑板承载 flags、inventory、chosen options、counters 等长期状态，供条件出口和后续事件读取；即时分叉优先使用 Node 的选项路由映射。
- 原因：如果所有分支都通过“写 flag -> Transition 读 flag”实现，会把大量纯流程跳转污染进黑板。
- 备选方案：
  - 所有分支都走黑板：长期可组合性强，但即时分叉会变得绕。
  - 完全不引入黑板：无法表达延迟后果与跨节点条件。

### 6. 动态插入通过运行时队列完成，而不是改静态图
- 选择：当某个选择、条件或后续结果需要插入新节点时，运行时直接对待执行节点队列做插入，而不去修改静态图。
- 原因：静态图代表“可用内容结构”，运行时队列代表“本次实际流程”；动态事件属于运行时决策。
- 备选方案：
  - 在静态图上直接打补丁：会混淆配置层和运行态。

## Risks / Trade-offs

- [Risk] 从线性 route 切到图 + 队列后，流程调试复杂度会上升  
  → Mitigation：保留清晰的节点记录、黑板快照和待执行队列日志，方便定位为什么会走某条分支。

- [Risk] 黑板字段若设计过宽，会逐渐演变为杂项状态堆  
  → Mitigation：限定黑板只承载会被后续条件读取的长期状态，不把纯展示或纯临时变量塞进去。

- [Risk] 动态插入节点与条件出口并存时，顺序规则不明确会导致行为不可预测  
  → Mitigation：在实现中明确优先级，例如“先结算当前节点效果，再插入节点，再解析下一个出口”。

- [Risk] schema 调整后需要同步 `xlsx` 表结构和数据，agent 无法代为完成  
  → Mitigation：在 tasks 中单独列出手工改表步骤，由用户处理，agent 仅提供清单和说明。

## Migration Plan

1. 为远征 schema 增加节点级路由策略、Transition、OptionRoute 和 Condition 配置。
2. 为运行态增加远征黑板与待执行节点队列。
3. 将流程推进从 `CurrentNodeIndex` 迁移到待执行节点队列。
4. 让 Event 的选项输入返回稳定的 `OptionId`，并由当前 Node 决定如何根据该 `OptionId` 选择出口。
5. 引入条件出口判定与动态插入节点能力。
6. 在用户完成必要的 `xlsx` 手工调整后，生成配置并验证最小远征、选项分支和延迟插入事件。

## Open Questions

- 当前没有额外必须先决的问题。后续若需要支持更复杂的随机权重路由或子图复用，可以在本次模型之上继续扩展，而不是推翻 `RoutePolicy + Blackboard + PendingNodeQueue` 的基础结构。
