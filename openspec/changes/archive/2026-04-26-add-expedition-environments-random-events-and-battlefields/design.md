## Context

当前远征系统已经具备 Luban 静态配置、运行态推进、分支路由、动态插入节点、Combat 桥接和 `IExpeditionEffect` 执行接口。现有设计中 Event 只承担内容模板职责，Node 承担本次实例的路由语义；这条边界必须继续保持，否则同一个 Event 在多个 Node 中复用时会重新变得混乱。

本次变更引入三个互相协作的新概念：

- 随机事件池：远征运行时可激活的候选事件库，负责按权重提供随机 Event。
- 环境：远征运行时的当前环境状态，负责附带环境随机事件池和默认 Combat 场地列表。
- 场地：Combat 表现与障碍物承载 prefab，由遭遇显式指定或从当前环境中随机选择。

## Goals / Non-Goals

**Goals:**

- 让远征支持通过 `RandomEvent` 节点从当前激活随机事件池抽取事件内容。
- 让随机事件池按池内无放回运行，同时允许不同池子中相同 Event 分别被抽中。
- 让远征支持初始环境和通过 Expedition Effect 切换当前环境。
- 让环境进入/离开时只影响未来随机事件抽取，不回滚已经抽出或插入的节点。
- 让 Combat 遭遇支持显式场地；未显式指定时从当前环境场地列表按权重放回随机。
- 保持 Event 内容与 Node 路由语义分离：随机抽到的 Event 提供标题、描述、选项和 Effect，当前 `RandomEvent` Node 仍负责路由。
- 明确 agent 不修改 xlsx；schema 需要表格配合时暂停并通知用户。

**Non-Goals:**

- 本次不实现环境 Buff、GameTag、Buff 生命周期或阵营克制逻辑。
- 本次不实现随机事件冷却、全局一次性事件或按事件历史去重。
- 本次不让场地承担环境职责，例如环境 Buff、环境事件池和环境切换规则不放在场地中。
- 本次不创建美术资源，不手写 Unity `.meta` 文件。

## Decisions

### 1. 随机事件池使用“池运行态”而不是“事件历史”去重

每个激活池在本次远征运行态中维护自己的剩余可抽条目。抽中某个条目后，只从该池的剩余条目中移除它。

这样设计的原因是：用户明确要求不能通过“事件是否经历过”来阻止重复，因为外部 Effect 可能插入已经经历过的事件；同时不同池子配置同一个 Event 时，这个 Event 应当可以出现多次。池内无放回正好表达“这个池子里的候选不要重复消耗”，不会污染事件全局语义。

备选方案是按 `EventConfigId` 全局去重。该方案被排除，因为它会破坏多池复用同一 Event 的设计，也会让外部动态插入事件和随机抽取产生隐式耦合。

### 2. 随机抽取先选池，再选池内事件

运行时抽取时先计算所有激活且非空池的总权重，在总权重范围内抽取一个随机值，再按池顺序定位命中的池。定位池后，将全局随机值转换为池内局部随机值，再在该池剩余条目中按权重选择具体事件。

该算法与用户确认的规则一致，且使多个池子的相对权重可以自然叠加。实现时需要跳过空池和总权重小于等于 0 的池。

### 3. `RandomEvent` Node 使用抽到的 Event 内容，但路由仍由当前 Node 决定

`RandomEvent` 节点进入时抽取一个 Event 内容，并像普通事件一样展示该 Event 的标题、描述和选项。玩家选择后，选项的 `LstEffect` 按现有 Effect 系统执行；后续出口则使用当前 `RandomEvent` Node 的路由策略与选项映射。

这样可以继续复用“Event 是内容模板，Node 是流程实例”的现有原则。即使同一个 Event 被普通 Event 节点和多个 RandomEvent 节点使用，它们也可以拥有不同路由。

### 4. 空池跳过随机事件节点

当所有激活随机事件池都为空、权重无效或没有可抽条目时，`RandomEvent` 节点不弹出事件 UI，不生成一次事件选择，而是按该节点的默认/固定后续路由继续推进。

这样可以避免卡死远征，也让配置者可以安全放置“有随机内容则展示，没有则通过”的机会节点。

### 5. 环境切换只维护环境来源的激活池

远征运行态应区分随机事件池来源，例如远征基础池和当前环境池。进入新环境时添加新环境提供的池；离开旧环境时移除旧环境来源的池。已经抽出并作为节点执行或插入队列的事件不受影响。

该设计避免环境变更产生回滚副作用，也符合用户“动态移除事件池后，已抽出并插入的事件不需要移除”的要求。

### 6. 场地选择在 Combat 发起前完成并通过桥接传递

远征进入 Combat 节点时解析 Combat 遭遇配置：

- 如果遭遇显式配置了 `BattlefieldConfigId`，使用该场地。
- 如果未配置，则从当前环境的场地列表按权重随机选择。
- 场地抽取是放回的，不需要记录历史。
- 如果两者都无法提供有效场地，运行时应给出清晰错误并阻止 Combat 静默以错误场地开始。

选定场地 Id 通过 `CombatSessionRequest` 或等价桥接对象传给 Combat 层。`CombatBattlefieldConfig` 的读取与场地 prefab 创建归属于 `GameLogic.Gameplay.Combat.BattlefieldFactory`，远征侧不直接解析 Battlefield 配置。Combat 层按 `Assets/AssetRaw/Actor/Prefabs/Battlefield/{battlefield_config_id}` 规则加载同名 prefab，并通过 `Battlefield` 组件在对应出生区域中生成 Marble。

### 7. Luban schema 先改定义，xlsx 由用户手工修改

本次计划允许修改 xml schema 和对应代码使用方式，但不允许 agent 创建、编辑或填充 xlsx 表格。实现过程中如果 schema 变更导致需要补充表格列、sheet 或数据，执行者必须暂停并列出用户需要修改的内容，等待用户完成并生成代码后再继续。

## Risks / Trade-offs

- [Risk] 随机事件节点复用 Event 选项，但路由由 Node 决定，配置者可能误以为 Event 内部决定出口 → Mitigation：schema 命名、注释和任务说明中明确“Event 内容、Node 路由”的边界。
- [Risk] 环境切换时激活池来源管理错误，可能误删远征基础池或残留旧环境池 → Mitigation：运行态记录池来源，移除时只按环境来源移除。
- [Risk] 空池跳过节点可能让配置错误不明显 → Mitigation：运行时输出调试日志，说明随机事件节点因无可抽事件被跳过。
- [Risk] 场地缺失导致 Combat 无法正常展示 → Mitigation：Combat 发起前校验显式场地或当前环境默认场地，缺失时给出明确错误，不静默 fallback 到未知资源。
- [Risk] 后续 Buff/GameTag 引入后，环境职责可能膨胀 → Mitigation：本次只保存当前环境与配置引用，Buff 逻辑后续通过独立系统接入。
