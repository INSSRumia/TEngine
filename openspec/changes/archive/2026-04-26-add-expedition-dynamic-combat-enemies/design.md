## Context

当前远征已经具备阶段化奖励、环境、场地、分支路由和 Combat 桥接能力，但 Combat 敌人的强度仍缺少与远征进度配套的动态生成机制。现有 Combat 遭遇更适合表达“固定敌方编组”，一旦同一遭遇要复用于不同远征阶段，就容易出现复制配置、数值漂移和维护成本上升的问题。

用户已经明确了本次设计边界：

- 环境负责提供敌人类型候选池，暂不引入 `pool_tag`。
- 远征配置负责引用一套敌人强度档位配置。
- Combat 遭遇需要同时支持固定敌人和动态敌人。
- 动态敌人只配置数量档位和等级档位，具体敌人类型从当前环境的敌人池中抽取。
- agent 不允许修改任何 `xlsx`；schema 改完后必须暂停，等待用户手工改表并重新生成 Luban 代码。

## Goals / Non-Goals

**Goals:**

- 让远征支持独立的敌人强度档位配置，并按远征阶段解析敌人数量与等级。
- 让环境配置能够声明敌人候选池，作为动态敌人类型的来源。
- 让 Combat 遭遇同时支持固定敌人列表和动态敌人组。
- 让远征在进入 Combat 前生成最终敌方 roster，并通过既有桥接请求交给 Combat。
- 保持 Combat 与 Expedition 解耦，不让 Combat 直接理解远征动态敌人配置。
- 明确 schema 改动后的人工协作边界，避免 subagent 擅自改表。

**Non-Goals:**

- 本次不引入 `pool_tag`、敌人池标签筛选或多池切换策略。
- 本次不实现基于玩家战力、局外成长或全局公式的敌人自动缩放。
- 本次不改造 Combat 内部 Marble 生成逻辑之外的战斗 AI、Buff 或属性系统。
- 本次不创建、编辑或填充任何 `xlsx`，也不手写 Unity `.meta` 文件。

## Decisions

### 1. 使用独立的 `ExpeditionEnemyProfileConfig` 表达敌人强度

敌人强度不直接写在 Combat 遭遇里，而是通过独立的敌人档位配置进行解析。该配置至少提供“敌人数量档位”和“敌人等级档位”两类映射，并允许同一档位在 `early`、`mid`、`late` 等不同远征阶段解析出不同真实值。

这样设计的原因是：Combat 遭遇应该表达“这里可能打什么类型的战斗”，而不是承担所有进度数值缩放职责。将强度档位独立出来后，同一遭遇模板可以跨多个远征阶段复用。

备选方案是直接在动态敌人组里写死数量和等级。该方案被排除，因为它会重新把“内容模板”和“强度缩放”耦合到一起。

### 2. 环境只负责敌人类型候选，不负责数量和等级

环境中的敌人池条目只声明候选 `MarbleSpawnConfig` 和权重，不在环境层面决定本场实际生成多少个敌人，也不把候选等级视为最终战斗等级。

这样可以保持职责边界清晰：

- 环境回答“这里可能遇到什么种类的敌人”
- 动态敌人组回答“这场需要几只、按什么强度生成”
- 敌人档位配置回答“当前阶段该把档位解析成多少数量和多少等级”

### 3. Combat 遭遇保留固定敌人，并新增动态敌人组

首版不替换现有固定敌人能力，而是在遭遇中并存两类来源：

- 固定敌人：继续使用现有 `enemy_marbles` 或等价字段，适合 Boss、剧情指定敌人、特殊编组。
- 动态敌人组：只声明 `count_tier` 和 `level_tier`，适合随远征阶段浮动的常规敌人。

最终敌方 roster 由“固定敌人 + 动态敌人生成结果”拼接得到。这样可以避免为了保留少数指定敌人而让动态系统反向承担特例逻辑。

### 4. 动态敌人类型从当前环境池按权重放回抽取

每个动态敌人组在解析出最终数量后，按数量次数从当前环境敌人池中逐次抽取候选敌人类型。首版抽取采用放回方式，同一场 Combat 中允许多次抽到同一种候选。

这样做的优点是：

- 规则简单，配置者容易理解。
- 不需要为环境池维护“池内无放回”状态。
- 更符合“某类敌人是该环境常见敌人”的设计语义。

备选方案是无放回抽取。该方案会使小池子在高数量战斗中迅速抽空，并额外引入“抽空后如何处理”的规则，首版不划算。

### 5. 动态敌人等级覆盖候选 `MarbleSpawnConfig` 中的等级

环境池的候选 `MarbleSpawnConfig` 主要用于描述敌人类型、阵营和基础出生配置，但动态敌人的最终等级必须由动态敌人组解析出的等级覆盖。否则环境候选和强度档位会同时拥有等级来源，导致配置意义冲突。

### 6. 动态敌人解析在远征侧完成

远征进入 Combat 节点时，就要把动态敌人组解析成具体的敌方 Marble 列表，然后通过 `CombatSessionRequest` 或等价桥接对象把最终 roster 传给 Combat。Combat 层不直接读取远征动态敌人组，也不从环境配置中自行抽敌人。

这样可以保持跨域边界清晰：

- Expedition 决定“本场有哪些敌人”
- Combat 只负责“把给定敌人 roster 打起来”

### 7. 缺失环境敌人池时明确失败

如果某个 Combat 遭遇包含动态敌人组，但当前环境没有有效敌人候选池，系统必须报出清晰错误并阻止本场 Combat 静默开始。首版不做隐式 fallback 到固定默认敌人或空敌人队伍。

### 8. schema 改完后必须暂停，等待用户改表

本次变更一定会触及 Luban schema，因此实现流程必须分成两个阶段：

1. 修改 xml schema。
2. 暂停并通知用户修改 `xlsx`、重新生成 Luban 代码。

只有在用户确认表格和生成代码都完成后，才能继续写运行时代码。

## Risks / Trade-offs

- [Risk] 固定敌人和动态敌人组同时存在时，配置者可能误解两者优先级 → Mitigation：在 spec 和任务中明确“最终 roster = 固定敌人 + 动态敌人”，不是二选一关系。
- [Risk] 环境敌人池只配置了少量候选时，放回抽取可能导致同一种敌人出现过多 → Mitigation：首版接受该结果，并通过权重和候选丰富度交给配置控制。
- [Risk] 候选 `MarbleSpawnConfig` 与动态等级覆盖同时存在，容易产生“候选等级到底有没有用”的困惑 → Mitigation：在 schema 注释和设计文档中明确动态等级优先。
- [Risk] 若在远征侧和 Combat 侧都保留一部分敌人生成逻辑，会重新产生职责重叠 → Mitigation：在桥接 spec 中规定 Combat 请求必须携带已解析完成的敌方 roster。
- [Risk] schema 修改后如果 agent 继续推进未生成的新配置代码，会造成假实现或错误补丁 → Mitigation：tasks 中强制在 schema 修改后暂停，等待用户完成改表和生成代码。
