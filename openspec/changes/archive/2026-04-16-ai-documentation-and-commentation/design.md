## Context

项目当前已经围绕 Combat 系统、Factory 装配、RuntimeData 黑板、Luban 配置和 OpenSpec 逐步形成了一套相对稳定的内部结构，但这些知识大多存在于代码、局部注释和历史会话中。对于后续 AI 接手开发来说，仅靠源码本身并不足够：AI 缺少一个明确的阅读入口，也缺少模块级结构说明和 schema 级注释来快速理解系统边界。因此，本次设计不是简单“多写注释”，而是建立一套分层的 AI 可读信息体系。

这套体系需要同时覆盖三种载体：项目/模块文档、Luban XML 结构注释、关键代码注释。三者的职责不同：文档负责建立阅读路径和结构地图，XML 注释负责解释配置 schema 语义，代码注释负责解释复杂职责和不直观逻辑。只有把这三层分开设计，AI 才不会在大量重复注释中迷失。

## Goals / Non-Goals

**Goals:**
- 为 AI 和开发者建立项目级阅读入口，明确推荐阅读路径。
- 为 Combat、RuntimeData、Factory、Luban 配置等关键模块补充结构文档。
- 为战斗相关 Luban XML schema 增补能表达职责、边界和代码消费方式的结构化注释。
- 为关键代码补充必要注释，重点解释职责、黑板分区、结算流程和装配边界。
- 减少 AI 依赖“读完整个代码库后再猜”的情况。

**Non-Goals:**
- 不追求给所有代码文件逐行补满注释。
- 不把文档写成与代码重复的流水账。
- 不修改与 AI 阅读路径无关的普通业务说明或用户文档。
- 不把所有实现细节都挪到文档中替代源码。

## Decisions

### 1. 文档和注释按三层组织：项目入口 / 模块说明 / 代码与 schema 注释
- 选择：将 AI 可读信息拆为三层：
  - 项目级入口文档
  - 模块级结构文档
  - 代码与 XML schema 内部注释
- 原因：AI 首先需要结构地图，其次才是模块说明，最后才是实现细节。按这个顺序组织信息比直接到处补注释更有效。
- 备选方案：
  - 只补代码注释：信息碎片化，AI 仍然缺少全局视角。
  - 只写高层文档：落地细节仍然要靠猜。

### 2. Luban XML 注释要解释“职责和边界”，不是只解释字段字面含义
- 选择：在 `equip.xml`、`marble.xml`、`projectile.xml` 中补充对 bean 职责、字段语义类别、代码消费方式和边界关系的说明。
- 原因：这些配置文件是 AI 修改玩法参数和配置结构时最常读的入口，如果注释只写“这个字段是什么”，帮助仍然有限。
- 备选方案：
  - 继续保持零散说明：AI 很难从 schema 本身理解规则。

### 3. 关键代码注释聚焦职责和边界，而非重复代码字面意思
- 选择：只为 Factory、RuntimeData、核心结算与复杂能力补充必要注释。
- 原因：高质量少量注释比低质量大量注释更适合 AI。AI 最需要的是“这个类为什么存在”“它和相邻类如何分工”。
- 备选方案：
  - 为所有类平均补注释：维护成本高且噪声大。

### 4. 优先补 AI 阅读路径，而不是先刷 XML 或源码
- 选择：实施顺序优先为：
  - 项目级 AI 入口文档
  - Combat 模块文档
  - Runtime 黑板文档
  - Luban schema 注释
  - 关键源码注释
- 原因：只有先建立阅读顺序，后续增加的注释和模块文档才不会失去组织性。
- 备选方案：
  - 先从代码注释开刷：极易造成信息层级混乱。

## Risks / Trade-offs

- [Risk] 文档与代码可能再次漂移  
  → Mitigation：优先记录稳定结构和职责边界，不在文档中重复易变实现细节。

- [Risk] 过度补注释会导致噪声上升  
  → Mitigation：只对关键类、关键流程和关键 schema 增补注释，不做无差别注释填充。

- [Risk] XML 注释写得过长会反而影响 schema 可读性  
  → Mitigation：优先写职责、边界、消费方，避免把实现细节整段塞进 XML 注释。

- [Risk] 不同 agent 可能对“文档”和“注释”边界理解不一致  
  → Mitigation：在 tasks 中明确每类产物的目标和优先级，减少执行歧义。
