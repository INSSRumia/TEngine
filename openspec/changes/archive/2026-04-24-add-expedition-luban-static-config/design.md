## Context

当前远征最小循环已经具备入口、事件、Combat 与结算链路，但其静态内容仍由运行时代码直接声明，包括线性节点、事件文本、事件效果、敌方编队与奖励。这样的实现适合快速验证闭环，却不适合继续扩展远征外围内容，也与当前战斗系统已经采用的 Luban 配置流不一致。

本次设计的目标不是重做远征运行态，也不是扩展完整的家园或分支路线系统，而是把“远征静态配置”从手写类中剥离出来，收敛为一套可由 Luban 生成的配置结构。用户已经确认当前开发期继续沿用现有 JSON 检查流程，因此本次变更不处理 JSON/bytes 切换，只要求 schema、生成代码与运行时代码的消费边界清晰。同时需要把一个重要协作约束写入设计：agent 不允许直接创建和修改任何 `xlsx` 数据表，凡是需要补表或改表的步骤都必须停下来通知用户手工处理。

## Goals / Non-Goals

**Goals:**
- 将当前远征中的静态 config 类迁移为 Luban schema 与生成代码。
- 为远征建立稳定的配置拆分：远征主流程表、事件表、Combat 遭遇表。
- 让远征节点保持首版线性结构，由配置中的节点列表顺序驱动。
- 保持事件效果为第一版最小固定字段，不提前引入多态事件效果系统。
- 让远征运行时代码读取 Luban 生成配置，而不是继续依赖硬编码工厂数据。
- 在计划与任务中明确人工边界：agent 不修改 `xlsx`，仅修改 schema、运行时代码和生成结果代码路径。

**Non-Goals:**
- 不在这次变更中实现分支路线、随机路网或权重选路。
- 不在这次变更中扩展复杂事件效果、多态事件能力或 Buff 配置体系。
- 不在这次变更中配置化家园系统、成长线或局外元进度。
- 不在这次变更中调整 JSON/bytes 生成与加载流程。
- 不要求 agent 直接补齐 `Configs/GameConfig/Datas/*.xlsx` 的数据内容。

## Decisions

### 1. 远征静态配置按“三表 + 若干 bean”拆分
- 选择：新增 `Gameplay.Expedition` 命名空间下的远征 Luban schema，并采用三张主表拆分：
  - `TbExpedition`：远征入口、名称、线性节点列表
  - `TbExpeditionEvent`：事件定义、选项、固定效果
  - `TbExpeditionCombatEncounter`：Combat 遭遇定义、敌方 Marble、奖励
- 原因：这能把“流程骨架”“事件内容”“战斗遭遇内容”解耦，既方便后续扩展，也能避免一张总表同时承担所有语义。
- 备选方案：
  - 单张大表：最省事，但事件与遭遇内容会快速膨胀，后续维护成本高。
  - 为每种节点单独建表并再做更细分拆表：过早复杂化，不适合当前最小循环阶段。

### 2. 节点采用线性列表与显式引用，而不是首版就上分支图
- 选择：远征主表中的 `route` 使用线性 `list`，每个节点包含 `node_type` 与对应引用字段，通过 `event_id` 或 `combat_encounter_id` 指向具体静态内容。
- 原因：用户已确认首版只需要线性节点列表，这样可以直接替换当前 `Event -> Combat` 的最小路线，不会把复杂图结构提前引入运行态。
- 备选方案：
  - 分支图或随机图：更灵活，但会立刻增加运行态选择逻辑、UI 呈现和配置复杂度。

### 3. 事件效果保持固定字段结构
- 选择：事件效果首版只保留固定字段，如 `crystal_delta`、`exp_delta`、`hp_delta`、`summary`。
- 原因：这与当前最小事件系统完全对齐，可以最低风险地从硬编码迁到配置，同时避免为了少量效果引入新的多态能力体系。
- 备选方案：
  - 事件效果多态 bean：未来可能需要，但当前收益不足。
  - 事件效果全自由键值对：对 AI 和代码都不稳定。

### 4. 运行态与静态配置继续严格分层
- 选择：仅迁移 `ExpeditionNodeConfig`、`ExpeditionEventNodeConfig`、`ExpeditionEventOptionConfig`、`ExpeditionCombatNodeConfig`、`ExpeditionEnemyMarbleConfig` 这一类静态内容；`ExpeditionRunState`、`ExpeditionNodeRecord`、`MarblePersistentData`、`CombatSessionResult` 等运行时/持久化结构继续手写。
- 原因：静态配置由 Luban 生成，运行态和持久化态由代码维护，这是当前项目战斗系统已经证明有效的边界。
- 备选方案：
  - 将运行态结构也统一做成配置风格类：会混淆静态数据与动态状态，后续只会更难维护。

### 5. 首版通过运行时适配层平滑接入，不强求一次性删除所有旧类
- 选择：先让 `ExpeditionFlowController` 与相关工厂/桥接逻辑从 Luban 配置读数据；旧的手写静态 config 类在迁移完成前可以暂时保留为适配过渡，但最终不再作为静态数据源。
- 原因：这样能降低一次性重构风险，也更适合当前已有最小循环在运行中的状态。
- 备选方案：
  - 一步到位删除所有旧静态类：最终状态更干净，但联调风险更高。

### 6. 人工改表边界写入任务，而不是让 agent 自动补数据
- 选择：本次 change 明确规定 agent 不能创建或修改任何 `xlsx` 表；若 schema 变更需要同步数据表，必须在任务和说明中把该步骤标记为“通知用户手工修改”。
- 原因：这是用户明确给出的协作约束，必须前置固化，否则后续 subagent 很容易误把改表也当成自己的工作范围。
- 备选方案：
  - 允许 agent 自动改表：与用户要求冲突。

## Risks / Trade-offs

- [Risk] 远征当前硬编码结构与 Luban 生成结构名称不完全对齐，迁移时容易出现新旧字段并存  
  → Mitigation：在运行时新增明确的配置读取/适配边界，逐步替换原有静态来源，避免半改半留但来源不明。

- [Risk] `xlsx` 不能由 agent 修改，可能造成 schema 完成后数据未及时补齐，导致实现卡在联调阶段  
  → Mitigation：在 tasks 中显式标出人工步骤，第一时间通知用户手工改表，而不是拖到最后才暴露。

- [Risk] 首版只支持线性节点与固定事件效果，会限制远征玩法表达力  
  → Mitigation：在 schema 命名和表拆分上预留扩展空间，但本次实现仍以最小闭环为准。

- [Risk] 继续沿用开发期 JSON 检查流，可能让后续切换 bytes 时仍需做一次验证  
  → Mitigation：本次不碰生成格式，只保证 schema 和运行时代码的语义边界稳定，为后续切换保留清晰入口。

## Migration Plan

1. 在 `Defines` 中新增远征相关 schema，并注册新的远征主表、事件表与遭遇表。
2. 通知用户根据新增 schema 手工维护对应的 `xlsx` 数据表与 `__tables__.xlsx` 注册项。
3. 运行 Luban 生成远征配置代码与 JSON 数据输出。
4. 在远征运行时代码中接入新的生成配置读取路径，用 Luban 数据替换硬编码静态来源。
5. 保留运行态与持久化结构不变，验证最小远征仍按线性事件到 Combat 的流程推进。
6. 清理已经失去职责的手写静态 config 来源或将其收敛为纯运行时辅助结构。

## Open Questions

- 当前无额外架构性未决问题；后续若需要扩展分支路线、复杂事件效果或更多远征节点类型，应以新增 schema 能力的方式递增设计，而不是在本次 change 中提前混入。
