## Context

当前战斗系统的配置定义主要集中在 `equip.xml`、`marble.xml`、`projectile.xml`，其中已经形成了一定的 bean 分层，但仍存在几类会持续放大维护成本的问题：行为语义靠 `int + 注释` 表达、时间字段类型不统一、主能力字段与扩展能力字段边界不够清晰，以及部分能力真实规则更多存在于注释而不是 schema 结构本身。对于 AI 辅助开发来说，这些问题会直接降低搜索准确性、代码生成稳定性和配置改动的可预测性。

本次设计的目标不是重做整套配置系统，而是把当前最容易误判、最容易继续发散的部分收敛成一套稳定约定。实现上优先考虑低风险高收益的调整：先枚举化行为字段、统一关键数值类型和命名，再逐步梳理主能力字段与扩展能力字段的归属。

## Goals / Non-Goals

**Goals:**
- 让战斗系统 Luban 配置本身更能表达语义，减少对长注释和 magic number 的依赖。
- 为 AI 和开发者建立统一的配置命名、字段类型和 bean 分层约定。
- 让工厂层能够依赖更稳定的配置结构，不必继续容忍“字段含义靠上下文猜”的情况。
- 优先收敛高频、低风险的配置问题，例如行为枚举和时间字段类型。
- 为后续继续清理配置到代码映射逻辑提供更稳定的 schema 基础。

**Non-Goals:**
- 不在这次变更里把所有默认能力都改成配置驱动。
- 不重做 Excel 数据表内容或一次性迁移所有历史配置字段命名。
- 不引入过度通用的超级能力配置协议。
- 不改变 Luban 本身的生成流程，只调整项目自有配置定义和对应代码消费方式。

## Decisions

### 1. 先处理行为型 `int` 字段的枚举化
- 选择：优先把 `shoot_type` 这类行为型 `int` 字段改为显式 `enum`。
- 原因：这是当前收益最高、风险最低的一类优化。它能同时提升 AI 理解能力、代码搜索能力和配置可读性。
- 备选方案：
  - 保持 `int + 注释`：改动最少，但语义仍然脆弱。
  - 一次性枚举化全部可疑字段：风险过高，建议分阶段推进。

### 2. 统一关键数值字段的命名与类型
- 选择：为时间、角度、角速度、加速度、普通速度建立稳定命名和类型约定，并优先修正明显不合理的字段，例如将生命周期时间从 `int?` 收敛为 `float?`。
- 原因：字段类型和命名是 AI 最主要的语义来源。只要这些基础约定稳定，后续代码消费和配置变更都会显著更可靠。
- 备选方案：
  - 暂时只改注释：无法解决代码层和 AI 层的实际误判问题。

### 3. 固定主能力字段与扩展能力字段分层保持两级结构
- 选择：继续保留“主能力独立字段 + 扩展能力 `lst_ability`”的双层结构，但通过规范明确：
  - 主能力字段用于该装备/对象运行所必需的参数能力
  - `lst_ability` 用于扩展玩法能力
- 原因：这比把所有能力都塞进一个列表更稳定，也比当前“虽然有两级，但规范不明确”更适合长期演化。
- 备选方案：
  - 所有能力都进 `lst_ability`：表达力强，但会削弱骨架稳定性。
  - 所有能力都拆成独立字段：扩展性太差。

### 4. 让结构表达规则，注释退居补充说明
- 选择：优先通过 `enum`、bean 层级和字段命名表达核心规则，注释只做补充而不是承载主要语义。
- 原因：注释对人有帮助，但对 AI 来说不是稳定契约。schema 本身必须足够自解释。
- 备选方案：
  - 继续依赖注释：短期省事，但未来问题会重复出现。

## Risks / Trade-offs

- [Risk] 字段类型和枚举变更会影响已生成代码和现有配置表内容  
  → Mitigation：分阶段推进，优先改动最小且易于迁移的字段，并在工厂消费代码中同步调整。

- [Risk] 过早追求“完全统一”可能引发不必要的大规模表结构改动  
  → Mitigation：仅处理高收益问题，保留当前有效的双层配置结构。

- [Risk] 某些注释中隐藏了尚未显式结构化的玩法约束  
  → Mitigation：迁移时优先把关键规则升级为 schema 结构，其余规则先保留注释补充说明。

- [Risk] 不同 agent 接手时可能继续重复讨论“配置应不应该全配置化”  
  → Mitigation：在 proposal、spec 和 tasks 中明确本次变更不追求全配置化，只做配置规范化。
