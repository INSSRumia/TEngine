## Context

当前 `Marble` 目录已经形成了 `ASC<T>` 宿主、`Ability<T>` 行为扩展、`MarbleRuntimeData` 运行时数据和 `MarbleFactory` 创建入口的基本结构。现状中所有 Ability 默认都参与 `OnUpdate`，部分能力再额外参与 `OnFixedUpdate`，使升级检测、伤害结算、死亡判定这类低频或事件型逻辑也被纳入逐帧轮询。

该问题在原型阶段影响有限，但项目 GDD 已明确后续会引入 Buff、将军技能、撤退、命名士兵死亡叙事等更多状态链路。如果继续沿用“所有能力统一轮询”的方式，热更层战斗循环会持续增长，且能力职责边界不清晰，不利于后续扩展与性能分析。

本次设计需要在不改变 Marble 对外业务语义的前提下，重构能力执行模型，使持续性逻辑继续支持帧轮询，而由状态变化触发的逻辑转为显式触发。

## Goals / Non-Goals

**Goals:**
- 为 Ability 增加明确的执行类型边界，区分 `Update`、`FixedUpdate` 和事件型能力。
- 让 `ASC<T>` 只维护必要的轮询列表，减少空跑。
- 为伤害、死亡、升级等结算型逻辑建立统一触发入口，避免每帧被动检测。
- 保持 Marble 现有战斗结果不变，为后续 Buff 和将军技能扩展预留稳定接入点。

**Non-Goals:**
- 不在本次变更中重新设计完整 Buff 系统。
- 不修改 GDD 层面的战斗规则，不新增面向玩家的能力表现。
- 不在本次变更中引入新的外部依赖或全项目级 Entity 框架重构。

## Decisions

### 1. Ability 执行模型采用“声明式分类 + 宿主分流”
- 决策：为 `Ability<T>` 增加执行声明，例如是否参与 `Update`、是否参与 `FixedUpdate`、是否仅响应显式事件。
- 原因：相比继续通过空实现方法统一遍历，这种方式能最小化对现有结构的破坏，并能直接在宿主层减少无效调用。
- 备选方案：
  - 方案 A：保留当前统一遍历，只在 Ability 内提前 `return`。缺点是空跑仍然存在。
  - 方案 B：彻底改成事件总线驱动全部能力。缺点是改动过大，不适合当前阶段。

### 2. `ASC<T>` 拆分能力容器为轮询列表与全量列表
- 决策：宿主继续持有完整 Ability 集合，同时额外维护 `UpdateAbilities` 与 `FixedUpdateAbilities` 两个缓存列表，仅分发给声明需要轮询的能力。
- 原因：这样既保留统一管理和优先级排序能力，也能避免在每帧对所有 Ability 做执行资格判断。
- 备选方案：
  - 仅在循环时根据标记过滤。实现简单，但每帧仍要判断一次。
  - 为每类 Ability 建立独立宿主。结构过重，不适合当前 Marble 规模。

### 3. 结算型逻辑通过显式入口触发，而不是逐帧观察
- 决策：将伤害结算、死亡判定、升级检测改为由宿主或战斗系统在状态变化后调用统一结算入口，例如“应用待处理数值”“经验变化后检测升级”“生命值变化后检测死亡”。
- 原因：这些逻辑天然是离散事件，不应依赖每帧 polling；显式触发更易定位时序，也更适合以后接入命中、击杀、Buff 触发链。
- 备选方案：
  - 保留逐帧检测并增加脏标记。虽然能减少部分逻辑执行，但仍保留轮询框架。
  - 在 `RuntimeData` 的属性 setter 内自动触发。会让数据对象承担过多行为，且时序隐蔽。

### 4. 物理驱动类能力继续留在 `FixedUpdate`
- 决策：移动、旋转、物理参数同步等持续型能力仍通过 `FixedUpdate` 运行。
- 原因：这类逻辑与 `Rigidbody2D` 强相关，保持在固定帧最符合现有 Unity 物理模型，也利于维持当前战斗表现。
- 备选方案：
  - 将移动改为事件驱动脉冲式更新。会破坏当前持续加力模型，不适合弹珠战斗。

### 5. 本次只约束 Marble 层，不扩展到全部实体框架
- 决策：规范先在 `Marble` 战斗域落地，并通过 spec 修改 `entity-lifecycle-module` 的实体宿主能力调度要求，而不是马上全项目替换。
- 原因：当前问题集中在 Marble 战斗原型，局部收敛风险更低，也更容易验证收益。
- 备选方案：
  - 直接统一所有 Entity/Ability 框架。范围过大，容易阻塞战斗原型推进。

## Risks / Trade-offs

- [Risk] 事件型触发入口分散，可能导致漏调某些结算链路  
  → Mitigation：统一由 `ASC<T>` 或专用战斗宿主提供少量明确入口，避免由外部代码随意直接调用 Ability。

- [Risk] 从轮询改为显式触发后，执行时序变化可能改变现有行为  
  → Mitigation：先保持原有优先级顺序与结算顺序不变，只改变触发时机，并在实现阶段补充最小验证用例。

- [Risk] 宿主维护多份 Ability 列表会增加管理复杂度  
  → Mitigation：将列表构建和排序封装在 `AddAbility/RemoveAbility` 内，外部不暴露维护细节。

- [Risk] 未来 Buff 系统接入后再次出现分类膨胀  
  → Mitigation：在本次模型中明确“轮询型/物理型/事件型”三类基础边界，后续 Buff 统一依附于该模型而不是再引入新轮询方式。
