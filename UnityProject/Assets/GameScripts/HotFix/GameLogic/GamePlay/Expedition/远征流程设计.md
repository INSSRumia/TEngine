# 远征流程设计

本文档描述当前远征系统在代码中的实际落地方式，供 AI 与开发者快速理解 `家园入口 -> 远征 -> 事件/随机事件/战斗 -> 结算` 的运行边界。

## 1. 当前范围

当前远征已经从早期写死的最小线性流程，演进为 Luban 配置驱动的最小可扩展远征框架。

已实现：

- 从 `InitialConfig -> CampConfig` 初始化玩家初始 money、初始 Marble 和可用远征列表
- 通过 `ExpeditionConfig.route` 配置远征节点
- 支持 `Event`、`RandomEvent`、`Combat` 三类节点
- 支持固定出口、按选项出口、按条件出口
- 支持运行时黑板条件，包括 flag、item、chosen option、counter 以及与/或/非组合条件
- 支持事件选项和 Combat 胜负结果触发 `IExpeditionEffect`
- 支持随机事件池，并在池内无放回抽取
- 支持环境，环境可提供随机事件池和 Combat 场地候选
- 支持通过 Effect 切换环境
- 支持远征向 Combat 传递 `BattlefieldConfigId`，由 Combat 层创建场地

当前仍不在本文档覆盖的已完成范围内：

- 完整家园玩法
- 正式磁盘存档
- 撤退流程
- 环境 Buff / GameTag 匹配
- 事件池冷却、全局唯一事件、一次性事件

## 2. 术语约定

- `Combat` 表示战斗域，不再引入并行的 `Battle*` 命名。
- `ConfigId` 表示配置表中的静态 Id，例如 `ExpeditionConfigId`、`NodeConfigId`、`EventConfigId`。
- `InstId` 表示运行时实例 Id，例如 `ExpeditionInstId`、`QueueEntryInstId`、`CombatSessionInstId`。
- `Node` 指远征路线上的单个推进单元，由 `ExpeditionRouteNodeConfig` 配置。
- `Event` 只提供展示内容、选项和 Effect，不直接拥有路线出口语义。
- `Transition` 是 Node 自己配置的出口。
- `ExpeditionNodeRecord` 表示某个节点在本次运行中的实际执行记录。
- `CombatSide` 表示战斗内敌我归属，不等同于 `camp_config_id`。
- `camp_config_id` 表示世界观/外观/颜色等配置阵营，可同时用于玩家与敌人的 Marble 外观来源。

## 3. 配置结构

### 3.1 开局配置

`InitialConfig` 只记录玩家当前使用的初始阵营配置 Id。

`CampConfig` 负责描述一个开局阵营：

- 初始 money
- 初始 Marble 列表
- 初始可用远征列表
- 阵营颜色等表现相关数据

运行时通过 `ExpeditionPersistentDataStore` 从这些配置初始化局外数据。

### 3.2 远征配置

`ExpeditionConfig` 是一次远征的静态定义：

- `expedition_config_id`：远征配置 Id
- `initial_environment_config_id`：远征开始时进入的环境
- `lst_random_event_pool_config_id`：远征基础随机事件池
- `route`：节点列表

基础随机事件池会在远征开始时激活，并在本次远征中持续存在。环境事件池会随环境切换动态移除和添加。

### 3.3 节点配置

`ExpeditionRouteNodeConfig` 描述一个远征节点：

- `Event` 节点使用 `event_config_id` 指定事件内容
- `RandomEvent` 节点从当前激活的随机事件池抽取事件内容
- `Combat` 节点使用 `combat_encounter_config_id` 指定战斗遭遇
- `route_policy` 决定节点如何选择后续出口

`FixedNext` 会选择优先级最高的出口。  
`BySelectedOption` 会根据玩家选择的 `option_id` 匹配 `option_routes`。  
`ByConditions` 会在所有满足条件的出口中选择优先级最高者。

### 3.4 条件配置

条件配置由 `ExpeditionConditionConfig` 派生：

- `HasFlagConditionConfig`：判断远征黑板是否存在 flag
- `HasItemConditionConfig`：判断远征黑板是否存在 item
- `HasChosenOptionConditionConfig`：判断本次远征是否选择过指定 option
- `CounterAtLeastConditionConfig`：判断计数器是否达到下限
- `AndConditionConfig`：所有子条件都满足
- `OrConditionConfig`：任意子条件满足
- `NotConditionConfig`：对子条件结果取反

条件只用于路由判断，不应该把 Event 的复用语义和 Node 的出口语义混在一起。

### 3.5 随机事件池

`ExpeditionRandomEventPoolConfig` 是随机事件候选库。

运行规则：

- 每个激活池在运行态保存自己的剩余条目
- 同一个池内无放回，抽中后从该池移除
- 不做全局 Event 去重
- 如果两个池都配置了相同 `event_config_id`，该事件可以分别从两个池中出现
- 抽取时先按所有有效激活池的总权重定位池，再用局部权重抽取池内事件
- 空池、总权重小于等于 0 的池不参与抽取
- 所有池都不可用时，`RandomEvent` 节点跳过事件展示并继续默认路由

`RandomEvent` 节点抽到的 Event 只提供标题、描述、选项和 Effect。后续出口仍由当前 `RandomEvent` 节点自己的 `route_policy` 决定。

### 3.6 环境

`ExpeditionEnvironmentConfig` 描述远征当前所处环境。

当前环境负责两件事：

- 提供环境来源的随机事件池
- 提供 Combat 未显式配置场地时的场地候选列表

环境切换规则：

- 切换时移除旧环境来源的激活随机事件池
- 添加新环境来源的随机事件池
- 不移除远征基础随机事件池
- 不回滚已经抽出、插入或执行过的事件
- 不应用环境 Buff，Buff / GameTag 是后续扩展

`ChangeEnvironmentEffectConfig` 会通过统一的 `IExpeditionEffect.Execute(context)` 修改 `ExpeditionRunState.CurrentEnvironmentConfigId`，并触发环境事件池更新。

## 4. 运行时数据边界

### 4.1 局外层

`MarblePersistentData` 是局外 Marble 数据结构，包含：

- `MarbleInstId`：运行时唯一实例 Id
- `MarbleConfigId`：Marble 配置 Id
- `CampConfigId`：阵营配置 Id，用于外观、颜色等长期身份信息
- 等级、生命、经验、死亡状态

`ExpeditionPersistentDataStore` 是当前阶段的运行期入口数据容器，保存局外 Marble 列表、money 和上次远征结果。当前还不是正式磁盘存档。

### 4.2 远征层

`ExpeditionRunState` 是一次远征的总运行态：

- 当前远征实例和配置 Id
- 当前待执行节点队列
- 当前环境
- 当前激活随机事件池
- Marble 运行快照
- 节点执行记录
- 调试日志和结束原因

`ExpeditionNodeRecord` 记录单个节点的执行结果，包括：

- 实际执行的 Node
- 随机事件实际抽到的 Event
- 玩家选择的 option
- Combat 结果
- Effect 摘要
- 路由决策摘要
- 动态插入节点记录

### 4.3 Combat 边界

远征层只通过数据包和 Combat 域交互：

- `CombatSessionRequest`：远征传给 Combat 的输入，包含友方 Marble、敌方 Marble、Combat 遭遇 Id 和 `BattlefieldConfigId`
- `CombatSessionResult`：Combat 返回给远征的唯一结算来源

远征层不直接读取 Combat 场景对象来做结算。Combat 内部死亡、经验、血量等结果必须通过 `CombatSessionResult` 回到远征。

## 5. Effect 系统

远征 Effect 统一实现 `IExpeditionEffect`。

当前第一批 Effect：

- `AddMoneyEffect`：修改远征局内 money
- `AddPlayerMarbleExpEffect`：修改玩家 Marble 经验
- `AddPlayerMarbleHpEffect`：修改玩家 Marble 当前 HP
- `ChangeEnvironmentEffect`：切换当前环境

Effect 通过 `ExpeditionEffectContext` 获取执行所需上下文，不应在 Effect 构造函数里持有运行态引用。配置数据来自 Luban，运行数据来自 Execute 时传入的 context。

Event 选项、Combat 胜利结果、Combat 失败结果都可以配置 `lst_effect` 类列表，用同一套 Effect 管线结算。

## 6. FSM 设计

`ExpeditionFlowController` 是远征流程 owner，使用 TEngine FSM 驱动，并通过分部类拆分不同职责。

状态集合：

- `ExpeditionFlowStatePrepare`
- `ExpeditionFlowStateEnterNode`
- `ExpeditionFlowStateEvent`
- `ExpeditionFlowStateCombat`
- `ExpeditionFlowStateApplyNodeResult`
- `ExpeditionFlowStateSettlement`
- `ExpeditionFlowStateFinished`

关键约束：

- 只有 `ExpeditionFlowController` 接收事件选择和 Combat 结果
- UI 只提交输入，不直接跳状态
- Combat 结果到达后，先回写节点记录和 Marble 结果，再决定是否继续路由
- Summary 记录应由 `ExpeditionNodeRecord` / `ExpeditionRunSummary` 相关类型负责，控制器只调用方法，不拼接大段摘要逻辑

## 7. Combat 场地桥接

远征只负责选择本场 Combat 使用哪个 `BattlefieldConfigId`：

1. Combat 遭遇配置了有效 `battlefield_config_id` 时，优先使用遭遇显式场地。
2. 遭遇没有显式场地时，从当前环境 `lst_battlefield` 中按权重随机选择。
3. 环境场地选择是放回的，不记录历史，也不会从候选中移除。
4. 如果最终无法得到有效场地，远征应输出清晰错误，不静默启动未知场地 Combat。

场地配置和 prefab 加载属于 Combat 域，由 `BattlefieldFactory` 负责。远征不应通过 `ExpeditionConfigBridge` 读取 `CombatBattlefieldConfig`。

## 8. UI 约束

远征相关 UI 必须遵循 TEngine `UIWindow/UIModule` 流程：

- `ExpeditionMainUI` 承担入口与出征准备
- `EventCardUI` 承担事件节点输入
- `ExpeditionResultUI` 承担远征结果展示

当前阶段只做功能型 UI，不等待美术资源。

如果后续要创建或修改 Unity 场景、Prefab、Canvas 层级或组件挂载，必须通过 Unity MCP 完成。不要手写 `.meta` 文件；如果编译或资源问题疑似 Unity 未刷新，通知用户回 Unity 刷新。

## 9. 配置修改约束

AI 可以修改 Luban XML schema 与运行时代码，但不允许创建、编辑或填写 xlsx 表格。遇到必须修改表格内容时，应暂停并通知用户手工修改表格并重新生成 Luban 代码。

修改 schema 后，必须明确说明需要用户更新哪些表格、哪些 sheet、哪些字段。
