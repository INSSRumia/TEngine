# 远征流程设计

本文档描述当前远征系统在代码中的实际落地方式，供 AI 与开发者快速理解 `家园入口 -> 远征 -> 事件/随机事件/Combat -> 结算` 的运行边界。

## 1. 当前范围

当前远征已经从最早的最小线性流程，演进为一套由 Luban 配置驱动、支持分支和运行时扩展的最小可扩展远征框架。

当前已实现：

- 从 `InitialConfig -> CampConfig` 初始化玩家开局 money、初始 Marble 和可用远征列表
- 通过 `ExpeditionConfig.route` 配置远征节点
- 支持 `Event`、`RandomEvent`、`Combat` 三类节点
- 支持 `FixedNext`、`BySelectedOption`、`ByConditions` 三种路由策略
- 支持运行时黑板条件，包括 flag、item、chosen option、counter，以及与/或/非组合条件
- 支持随机事件池，并在池内无放回抽取
- 支持环境切换，环境可动态增删随机事件池，并提供 Combat 场地候选
- 支持节点级动态插入，包括“立刻插入下一个节点”和“在指定节点后触发插入”
- 支持事件选项、Combat 胜负统一执行 `IExpeditionEffect`
- 支持奖励档位化解析，包括 money、经验、生命、招募数量和招募候选池
- 支持动态敌人生成：环境提供敌人类型候选，远征 enemy profile 提供数量和等级强度
- 支持 Effect summary 的命名 token 渲染，例如 `{money}`、`{count}`、`{marble_name}`
- 支持远征向 Combat 传递 `BattlefieldConfigId`，由 Combat 层创建场地并返回结算结果

当前仍不在本文档覆盖范围内：

- 完整家园玩法
- 正式磁盘存档
- 撤退流程
- 环境 Buff / GameTag 匹配
- 事件池冷却、全局唯一事件、一次性事件
- 更复杂的奖励公式系统、Buff 系统、Item 系统

## 2. 术语约定

- `Combat` 表示战斗域，不再引入并行的 `Battle*` 命名。
- `ConfigId` 表示配置表中的静态 Id，例如 `ExpeditionConfigId`、`NodeConfigId`、`EventConfigId`。
- `InstId` 表示运行时实例 Id，例如 `ExpeditionInstId`、`QueueEntryInstId`、`CombatSessionInstId`。
- `Node` 指远征路线上的单个推进单元，由 `ExpeditionRouteNodeConfig` 配置。
- `Event` 只提供展示内容、选项和 Effect，不直接拥有路线出口语义。
- `Transition` 是 Node 自己配置的出口。
- `ExpeditionNodeRecord` 表示某个节点在本次运行中的实际执行记录。
- `CombatSide` 表示战斗内敌我归属，不等同于 `camp_config_id`。
- `camp_config_id` 表示世界观/外观/颜色等配置阵营，可同时用于玩家与敌人的 Marble 外观来源。
- 代码内统一使用 `money` 表示资源数值；“晶体”只是当前文案层的展示叫法。

## 3. 配置结构

### 3.1 开局配置

`InitialConfig` 只记录玩家当前使用的开局阵营配置 Id。

`CampConfig` 描述一个开局阵营：

- `initial_money`
- `lst_initial_marbles`
- `lst_expedition`
- 阵营颜色等表现相关数据

运行时通过 `ExpeditionPersistentDataStore` 从这些配置初始化局外数据。

### 3.2 远征主配置

`ExpeditionConfig` 是一次远征的静态定义，当前重点字段包括：

- `expedition_config_id`
- `reward_profile_config_id`
- `enemy_profile_config_id`
- `initial_environment_config_id`
- `lst_random_event_pool_config_id`
- `route`

基础随机事件池会在远征开始时激活，并在本次远征中持续存在。环境事件池会随环境切换动态移除和添加。

### 3.3 节点配置

`ExpeditionRouteNodeConfig` 描述一个远征节点：

- `Event` 节点使用 `event_config_id` 指定事件内容
- `RandomEvent` 节点从当前激活随机事件池抽取事件内容
- `Combat` 节点使用 `combat_encounter_config_id` 指定战斗遭遇
- `route_policy` 决定节点如何选择后续出口
- `transitions` 定义节点出口
- `option_routes` 只在 `BySelectedOption` 下使用，用于把 `option_id` 映射到 `transition_id`

三种路由策略：

- `FixedNext`
  - 不再依赖“默认出口 Id”
  - 直接选择优先级最高的出口
- `BySelectedOption`
  - 根据玩家选择的 `option_id` 找到对应 `option_routes`
  - 再由 `option_routes.transition_id` 找到真正的 `transition`
- `ByConditions`
  - 在所有满足条件的出口中选择优先级最高者

### 3.4 条件配置

条件配置由 `ExpeditionConditionConfig` 派生：

- `HasFlagConditionConfig`
- `HasItemConditionConfig`
- `HasChosenOptionConditionConfig`
- `CounterAtLeastConditionConfig`
- `AndConditionConfig`
- `OrConditionConfig`
- `NotConditionConfig`

条件只负责路由判断，不应该把 Event 的复用语义和 Node 的出口语义混在一起。

### 3.5 随机事件池

`ExpeditionRandomEventPoolConfig` 是随机事件候选库。

运行规则：

- 每个激活池在运行态保存自己的剩余条目
- 同一个池内无放回，抽中后从该池移除
- 不做全局 Event 去重
- 如果两个池都配置了相同 `event_config_id`，该事件可以分别从两个池中出现
- 抽取时先按所有有效激活池的总权重定位池，再用局部权重抽取池内事件
- 空池、总权重小于等于 0 的池不参与抽取
- 所有池都不可用时，`RandomEvent` 节点跳过事件展示并继续默认路由

`RandomEvent` 节点抽到的 Event 只提供标题、描述、选项和 Effect。后续出口仍由当前 `RandomEvent` 节点自己的 `route_policy` 决定。

### 3.6 环境

`ExpeditionEnvironmentConfig` 描述远征当前所处环境。

当前环境负责三件事：

- 提供环境来源的随机事件池
- 提供 Combat 未显式配置场地时的场地候选列表
- 提供动态敌人的类型候选池

环境切换规则：

- 切换时移除旧环境来源的激活随机事件池
- 添加新环境来源的随机事件池
- 不移除远征基础随机事件池
- 不回滚已经抽出、插入或执行过的事件
- 不应用环境 Buff，Buff / GameTag 是后续扩展

`ChangeEnvironmentEffectConfig` 会通过统一的 `IExpeditionEffect.Execute(context)` 修改 `ExpeditionRunState.CurrentEnvironmentConfigId`，并触发环境事件池更新。

### 3.7 奖励档位配置

`ExpeditionRewardProfileConfig` 负责把事件里的“奖励档位”解析成真实结果。

它当前包含：

- `lst_money`
- `lst_exp`
- `lst_hp`
- `lst_marble_count`
- `lst_recruit_candidate`

其中：

- `ExpeditionStageTierIntValueConfig` 负责区分 `early / mid / late`
- `ExpeditionTierIntValueConfig` 负责把某个 `tier` 映射成某个具体数值
- `ExpeditionRecruitRewardCandidateConfig` 负责定义某个档位下可抽取的 `MarbleSpawnConfig` 与权重

也就是说：

- Event / Combat 配置声明“请求什么档位”
- RewardProfile 决定“这个档位在当前远征阶段等于多少”
- 运行时统一由 `ExpeditionRewardResolver` 解析真实值

### 3.8 敌人强度档位配置

`ExpeditionEnemyProfileConfig` 负责把 Combat 动态敌人组里的“数量档位 / 等级档位”解析成真实结果。

它当前包含：

- `lst_enemy_count`
- `lst_enemy_level`

这两组字段与奖励档位一样，复用同一套：

- `ExpeditionStageTierIntValueConfig`
- `ExpeditionTierIntValueConfig`

也就是说：

- Combat 动态敌人组声明“本组请求哪个 `count_tier` / `level_tier`”
- EnemyProfile 决定“这个档位在当前远征阶段等于多少”
- 运行时统一由 `ExpeditionCombatEnemyResolver` 解析真实数量与等级

### 3.9 Combat 遭遇配置

`ExpeditionCombatEncounterConfig` 负责描述 Combat 节点的战斗输入：

- 标题
- 固定敌方 `MarbleSpawnConfig` 列表
- 动态敌人组列表
- 可选的 `battlefield_config_id`
- `lst_victory_effect`
- `lst_defeat_effect`

遭遇显式配置了场地时优先使用该场地。否则由当前环境的场地候选按权重随机选择。

固定敌人和动态敌人的规则不同：

- 固定敌人直接使用 `enemy_marbles` 里各自配置的 `MarbleSpawnConfig.Level`
- 动态敌人先从当前环境 `lst_enemy_candidate` 抽“敌人类型”
- 抽到候选后，运行时会保留候选的 `marble_config_id` 和 `camp_config_id`
- 但最终 `level` 不使用候选里自带的值，而是由 `enemy_profile + level_tier + 当前阶段` 解析后覆盖
- 当前实现不会按环境候选里配置的 `level` 做筛选
- 可以把环境候选理解为“敌人类型池”，而不是“敌人最终属性池”

## 4. 运行时数据边界

### 4.1 局外层

`MarblePersistentData` 是局外 Marble 数据结构，包含：

- `MarbleInstId`
- `MarbleConfigId`
- `CampConfigId`
- `DisplayName`
- `Level`
- `CurrentHp`
- `MaxHp`
- `Exp`
- `IsDead`

`ExpeditionPersistentDataStore` 是当前阶段的运行期入口数据容器，保存：

- `Money`
- `LstMarbles`
- `LastResult`

当前它还不是正式磁盘存档，但它已经是“家园入口层看到的局外数据真值”。

### 4.2 远征层

`ExpeditionRunState` 是一次远征的总运行态，当前核心字段包括：

- `ExpeditionInstId`
- `ExpeditionConfigId`
- `CurrentEnvironmentConfigId`
- `Phase`
- `EndReason`
- `TotalMoneyGained`
- `Blackboard`
- `MarbleSnapshots`
- `Route`
- `PendingNodeQueue`
- `CurrentNodeEntry`
- `NodeRecords`
- `ScheduledInsertions`
- `LstActiveRandomEventPool`
- `DebugLogs`
- `PendingEventOptionId`
- `PendingCombatResult`
- `ResultSummary`
- `EnteredNodeCount`

### 4.3 队列与动态插入

当前远征流程不是“只有一个 current node 指针”，而是“待执行节点队列 + 当前节点”模型。

相关结构：

- `ExpeditionPendingNodeEntry`
  - 表示一个已经入队、等待执行的节点实例
  - 记录该节点从哪里来，是否为动态插入
- `ExpeditionScheduledNodeInsertion`
  - 表示一个“当触发某个节点后，再把另一个节点插入队列”的计划
  - 适合“前面埋伏笔，后面再出现”的设计

当前支持两种动态插入方式：

- `InsertNodeNext`
  - 立即插到队列头部，成为下一个执行节点
- `ScheduleNodeInsertionAfterNode`
  - 先记录计划，等某个 `triggerNodeConfigId` 被处理后再插入

### 4.4 节点记录与远征总结

`ExpeditionNodeRecord` 记录单个节点的执行结果，包括：

- 当前节点和来源节点
- 入队原因
- 实际执行顺序
- 路由策略
- 玩家选择的 `option_id`
- `RandomEvent` 实际抽到的 `event_config_id`
- 是否因空池跳过
- 当前节点获得的 money
- 解析出的出口
- 节点前后队列快照
- 节点前后黑板快照
- Effect 摘要
- 动态插入节点记录
- 路由决策日志
- Combat 结果

`ExpeditionResultSummary` 则在结算阶段汇总：

- 本次远征是否胜利
- 最终 `MoneyDelta`
- 所有 Marble 的最终状态
- 所有节点的摘要文本

## 5. 路由与阶段推进

### 5.1 FSM

`ExpeditionFlowController` 是远征流程 owner，使用 TEngine FSM 驱动，并通过分部类拆分职责。

状态集合：

- `ExpeditionFlowStatePrepare`
- `ExpeditionFlowStateEnterNode`
- `ExpeditionFlowStateEvent`
- `ExpeditionFlowStateCombat`
- `ExpeditionFlowStateApplyNodeResult`
- `ExpeditionFlowStateSettlement`
- `ExpeditionFlowStateFinished`

### 5.2 主循环

主循环大致如下：

1. 创建 `ExpeditionRunState`
2. 激活远征基础随机事件池和初始环境
3. 将第一个 Node 入队
4. FSM 进入 `Prepare`
5. `EnterNode` 从队列取出当前节点并写入 `ExpeditionNodeRecord`
6. 根据节点类型进入 `Event`、`RandomEvent` 或 `Combat`
7. 收到玩家选择或 Combat 结果后，进入 `ApplyNodeResult`
8. 执行 Effect、触发动态插入、解析路由出口、决定是否结算
9. 所有节点完成或满足结束条件后，进入 `Settlement`
10. 回写局外数据，展示结果 UI，再回到入口

### 5.3 结束条件

当前会触发结算的情况：

- `CurrentRun.EndReason != None`
- 没有待执行节点
- 玩家全部 Marble 阵亡

当前默认胜利条件是：

- 在没有被提前判负的情况下，所有待执行节点都处理完成

## 6. Effect 系统

远征 Effect 统一实现 `IExpeditionEffect`。

当前第一批运行时 Effect：

- `AddMoneyEffect`
- `AddPlayerMarbleExpEffect`
- `AddPlayerMarbleHpEffect`
- `AddPlayerMarbleEffect`
- `ChangeEnvironmentEffect`

### 6.1 执行上下文

`ExpeditionEffectExecutionContext` 在一次节点结算时提供：

- `RunState`
- `PersistentData`
- `NodeRecord`
- `RewardContext`
- `SummaryLines`

其中 `RewardContext` 会在构造时自动从当前远征运行态和节点记录推导出：

- 当前远征配置
- 当前 `RewardProfile`
- 当前 `ProgressStage`
- 当前节点序号
- 节点总数

### 6.2 奖励解析

奖励型 Effect 不再直接读取固定数值字段，而是统一通过 `ExpeditionRewardResolver` 取真实值。

当前支持解析：

- `ResolveMoney`
- `ResolveExp`
- `ResolveHp`
- `ResolveMarbleCount`
- `ResolveRecruitCandidate`

这意味着：

- 同一个 Event 文案可以在不同远征里复用
- 同一个档位可以在 `early / mid / late` 解析出不同结果
- 招募 Effect 可以从候选池中按权重抽实际 Marble，而不是写死兵种

### 6.3 Summary 渲染

Effect summary 支持命名 token，例如：

- `{money}`
- `{exp}`
- `{hp}`
- `{count}`
- `{marble_name}`

规则如下：

- 每个 Effect 自己提供 token 字典
- `ExpeditionEffectExecutionContext` 统一执行模板替换
- token 缺失时不静默吞掉，会保留原 token，并写入 `DebugLogs` 和 `NodeRecord.LstRouteDecisionLog`

## 7. Combat 边界

远征层只通过数据包和 Combat 域交互：

- `CombatSessionRequest`
- `CombatSessionInstId`
- `NodeConfigId`
- `CombatEncounterConfigId`
- `BattlefieldConfigId`
- `Title`
  - `LstAlliedMarble`
  - `LstEnemyMarble`
- `CombatSessionResult`
  - `IsVictory`
  - `Summary`
- `LstMarbleResult`

远征层不直接读取 Combat 场景对象来做结算。Combat 内部死亡、经验、血量等结果必须通过 `CombatSessionResult` 回到远征。

当前 `LstEnemyMarble` 的来源规则如下：

- 固定敌人直接来自 `ExpeditionCombatEncounterConfig.EnemyMarbles`
- 动态敌人来自 `ExpeditionCombatEncounterConfig.LstDynamicEnemyGroup`
- 动态敌人类型从当前环境 `LstEnemyCandidate` 按权重放回抽取
- 动态敌人最终等级由 `enemy_profile` 覆盖候选 `MarbleSpawnConfig.Level`

Combat 结果回到远征后：

1. 用 `LstMarbleResult` 覆盖当前远征里的对应 Marble 快照
2. 根据胜负执行 `lst_victory_effect` 或 `lst_defeat_effect`
3. 记录 Combat 节点摘要
4. 再参与后续路由与结算逻辑

## 8. 场地选择规则

远征只负责决定本场 Combat 使用哪个 `BattlefieldConfigId`：

1. Combat 遭遇配置了有效 `battlefield_config_id` 时，优先使用遭遇显式场地。
2. 遭遇没有显式场地时，从当前环境 `lst_battlefield` 中按权重随机选择。
3. 环境场地选择是放回的，不记录历史，也不会从候选中移除。
4. 如果最终无法得到有效场地，远征会输出清晰错误，不静默启动未知场地 Combat。

场地配置和 prefab 加载属于 Combat 域，由 `BattlefieldFactory` 负责。远征不应通过 `ExpeditionConfigBridge` 读取 `CombatBattlefieldConfig`。

## 9. UI 约束

远征相关 UI 必须遵循 TEngine `UIWindow/UIModule` 流程：

- `ExpeditionMainUI` 承担入口与出征准备
- `EventCardUI` 承担事件节点输入
- `ExpeditionResultUI` 承担远征结果展示

当前阶段只做功能型 UI，不等待美术资源。

如果后续要创建或修改 Unity 场景、Prefab、Canvas 层级或组件挂载，必须通过 Unity MCP 完成。不要手写 `.meta` 文件；如果编译或资源问题疑似 Unity 未刷新，通知用户回 Unity 刷新。

## 10. 配置修改约束

AI 可以修改 Luban XML schema 与运行时代码，但不允许创建、编辑或填写 xlsx 表格。遇到必须修改表格内容时，应暂停并通知用户手工修改表格并重新生成 Luban 代码。

修改 schema 后，必须明确说明需要用户更新哪些表格、哪些 sheet、哪些字段。
